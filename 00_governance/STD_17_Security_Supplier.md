# 情報保護・脆弱性・委託先技術回答

添付STD-10の開発記録・確認方法を反映した内部標準。IPA/JETの指定様式・制度必須期限・適合条件の代用にしない。

## 1. 情報と信頼境界

<a id="aim-22"></a>
### AIM-22 — 必要最小限の入力と脅威確認

組織が許可したアカウント・サービス・実行形態・データ分類に限定する。非公開リポジトリだから任意のAIへ入力可能とはしない。委託先の非公開資産は利用権・AI利用可否を確認する。鍵・パスワード・トークン・製品共通秘密は入力・出力・ログへ含めず、ダミーを使う。住宅・顧客データは必要性・権限を確認し、必要なマスク・匿名化・分離を行う。

漏えい時は再掲せず、対象・時点・影響を制限付き記録へ残し、既定権限と手順で報告・失効・更新を行う。問題の生成物を後続入力へ無条件に流さない。

変更に関係する①資産、②入口・信頼境界、③脅威と成立条件、④防止・検知・制限・復旧と残存リスク、⑤検証を簡潔に結ぶ。外部入力、認可、鍵、FW、暗号混在、制御権を重点確認する。

## 2. 構成情報・受付・技術判断

<a id="aim-23"></a>
### AIM-23 — 脆弱性対応と部品情報

部品名・版・取得元・patch/backport・組込先・連絡先・ライセンスを製品/HW/FWと関連付ける。正式SBOMがある場合は生成元と版を参照し、暫定一覧を形式適合としない。部品存在だけでコード到達性・利用設定・実影響を確定しない。

| 段階 | 記録 |
|---|---|
| 受付 | 受付ID、日時、報告元、対象候補、機密、担当・一次判断予定 |
| 対象特定 | 製品/HW/FW・部品・設定・露出経路、該当／非該当／調査中と根拠 |
| 技術分析 | 原因、成立条件、到達可能性、影響、不明点、方針 |
| 対応 | 暫定措置、修正物、差分、再現／回帰、更新／復旧 |
| 判断・連絡 | 自社の責任者・根拠、顧客・委託先・制度への対応要否と送信権限 |
| 終結 | 配布と適用の範囲、残課題、次の監視・証拠 |

期限は適用契約・制度・利用状況に基づいて担当者が設定する。24時間等を本標準で創作しない。未定でも認可内の受付・証拠保全・対象特定は進める。ラベル対象版や変更要否をAIが推定せず、正式根拠と担当者判断へ接続する。

## 3. 委託先に求める最小の回答

<a id="aim-24"></a>
### AIM-24 — ブラックボックスを推測で補わない

[Supplier Response](templates/Supplier_Response.md)で対象版、変更箇所、IF／データ／設定／既存機能への波及、必要な詳細設計、失敗・脆弱性成立条件、対策・残存、検証条件・結果・ログ、保守窓口・予定を求める。既存資料の文書ID・版・節・セル参照で代替してよい。全件で全ソフトの詳細設計を再提出させるのではなく、変更と不明な影響に絞る。

「影響なし」「問題なし」だけでは受入根拠として不足。確認した範囲、設定、コード又は試験を追加確認する。ソース非受領契約でも検証可能な差分説明・構成情報・試験証跡を確認し、内部構造をAIが推定して委託先確認済みにしない。

委託先回答は30_referencesへ原本を保存し、抽出・評価はanalysisへ、追加要求・修正案はdraftsへ置く。回答の受領、自社技術判断、製品受入、対外送信・出荷は別。
