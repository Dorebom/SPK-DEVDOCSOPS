# R8-FIX001：既存Word／Excelの抽出・マージと要求／USDM展開への準備性レビュー

## 1. 結論

**5部・44章の文書構造は再利用できる。しかし、既存Word／Excelを継続的に取り込み、矛盾を処理して仕様に採用し、要求・USDMへ展開する運用基盤としては、まだ補強が必要である。**

文書構造を再び全面再編する必要はない。追加すべきものは、主に「原資料→抽出項目→照合・判断→採用仕様」の管理層、USDMとの型付き対応、成長を許すデータ検査・一括更新である。

- 原資料の受領・隔離保存と、人が確認する小規模な抽出候補作成：開始可能。
- 現行の構造を分類先にした人手レビュー付き統合作業：受入ルールと出典台帳を追加する条件付きで可能。
- 現行ツールをそのまま使う連続的な追加・更新・自動マージ：推奨しない。
- 仕様文をそのまま「要求＋理由」に変換し、承認済みUSDMとして採用：不可。理由の根拠確認と要求の階層・適用・承認が必要。

本書は入力の改修やマージを実施した成果物ではない。補強案・未決事項は本レビューの提案であり、製品要求・権限・構成・認証の承認ではない。

`--baseline-check`では全OQがOPEN・回答nullであることも検査する。これはR8配布時点の未承認状態を保つ確認であり、将来OQを正当に解決する際の検査には使えない。廃止せず、版固定の監査と、編集・採用・リリースの検査を分けるべきである。

## 5. 不足する管理能力

### F01：取り込み原資料と抽出項目の追跡【先行対応】

現状は旧パッケージ・アーキテクチャ・CTX等の出典とハッシュを管理する。これは有用だが、「どの版のWordのどの表・段落」「Excelのどのシート・セル・注記」に基づく判断かを保持する一般的な抽出台帳はない。

追加する資料台帳には、文書ID、業務上の版、原本SHA-256、承認・適用範囲、受領日、As-Is／To-Be区分、閲覧制限、原本場所を持たせる。版を日付だけで判定しない。

抽出断片には原文、構造位置、隣接見出し・表ヘッダ・注記、取得方式・ツール版、未取得オブジェクト、確認状態を保持する。ページ番号だけでは編集やレンダラの違いでずれるため、原本ハッシュと段落・表・セル等の位置を組み合わせる。

### F02：抽出の完全性と解釈を分離【先行対応】

既存の文書QAにはWord／Excelの取り込み処理も抽出検査もない。単純なテキスト化を、資料全体の抽出完了と扱わない。

Wordでは見出し階層、段落順、入れ子・結合表、図・キャプション、脚注、変更履歴、コメントを対象化し、取得できない部分は明示する。python-docxの`paragraphs`は変更履歴内の段落を含まず、`tables`は入れ子表を含まないと公式資料に記載されている[S3]。どのライブラリを使うかとは別に、対応対象を列挙した抽出器と原本との対照確認が必要である。

Excelではセル値・式・保存済み計算値・表示書式・単位・結合範囲・非表示行列シート・注記・図形・外部参照を区別する。SpreadsheetMLの保存済み数式値は最終計算時のキャッシュである[S4]。原本を再計算して保存し直すことを抽出の既定動作にせず、原本値と再評価結果を別記録にする。マクロや外部リンクも無断実行しない。

.doc/.xls等の旧形式、保護文書、OLE、画像だけの仕様は対応範囲を決定する。画像は視認による照合対象とし、OCRなしでは読めない箇所だけを隔離して処置する。全体を無差別OCRする案ではない。

### F03：重複・矛盾・適用差の判断【先行対応】

現行の`decision_overrides.json`や`revision_changes.json`は特定改訂の記録であり、新しく取り込む任意資料に対する一般の競合台帳・判定規則ではない。製品の運転要求を調停するControl Arbiterや設定世代管理は、仕様文書同士のマージ機能ではない。

同値、追加、詳細化、適用条件差、矛盾、廃止、参照不足を分類し、判断前後・候補全文・適用範囲・根拠・決定者を記録する。少なくとも型式、HW/FW、リリース、As-Is／To-Be、通信経路、操作・測定点・時間基準、単位、状態、認証上の適用範囲が一致するか確認する。

例：旧Wordに「応答待ち2秒」、Excelに「5秒（PCS-B限定）」があっても、即座に矛盾／最新版優先とはしない。対象・応答段階・時計の起点を照合し、一般仕様と例外の関係か、真の競合かを判断する。この数値例は合成例であり、製品の仕様値ではない。

未承認のR8詳細案が、承認済み旧製品仕様を黙って置き換えてもいけない。旧仕様の事実はAs-Isへ保持し、To-Beとの差を設計変更・移行の判断として扱う。一方、旧図の誤記・省略を現在のルータ経路やH/G分離条件の自動変更根拠にも使わない。

### F04：要求・理由・仕様の構造とUSDMへの型付きリンク【先行対応】

124件の要求レコードすべてで`usdm_id=null`である。`source_requirement_text`があるのは24件で、出典のヒントとして活用できる。ただしこのフィールドもWord／Excelの文書版＋位置と結び付いた一般の抽出原文台帳ではない。

SYSレコードに`source_ids`と`basis`はあるが、要求階層、要求の理由、原子的仕様の分割関係、USDM→仕様の多対多関係を管理する完成済みモデルはない。個々の文の理由が他章に書かれている可能性まで否定するものではなく、構造化台帳としての不足である。

`S-FN`、`GW-FN`は機能群、`SYS`は現在のシステム要求、`OQ`は未決事項であり、そのままUSDMの「要求」「仕様」「理由」に一対一置換しない。機能群には複数の要求が対応し、単一のSYS文に分離可能な複数条件がある場合もある。既存IDを削除せず、親子・詳細化・派生・満たす・検証する等の関係で新しい要素へ接続する。

原文に理由がない場合は`reason=未確認`とし、AIが推定する場合は仮説と提案者・根拠を記録してレビューへ出す。もっともらしい理由を過去の要求意図として採用しない。

AFFORDDの公式USDM-SchemaはCanonical JSON、技術仕様、変換規則、移行ガイド等を公開している[S1]。採用候補として比較できるが、USDM技法を使うことと当該JSON Schemaへの適合は別である。採用時は版を固定し、出典・構成・役割などのプロジェクト管理属性を、規定の拡張方法又は別の対応台帳へ保持する。現在のJSONの`schema`文字列だけではスキーマ適合にならない。

### F05：文書管理データのスキーマと参照整合【先行対応】

現在の`schema`値は形式識別子であり、ZIPにそのJSON Schema定義と一般的な検証実装はない。型・必須・列挙・非空・ID一意性・参照先実在・適用版・双方向関係を検査する必要がある。承認済みにする際は、未解決の競合や未確認出典を禁止する等の状態遷移ルールも必要。

P02〜P07・P09が示すように、リンクや件数に問題がなくても管理レコードの意味的に重要な部分が壊れ得る。原本ハッシュは「その原本か」を示すもので、解釈や採用の正しさを証明しない。

### F06：データ増加と再取り込みへの拡張【先行対応】

件数はデータから求め、固定版監査の期待値は別プロファイルに隔離する。新規文書・機能・SYS・試験・OQ・機器プロファイルを追加したとき、検査器のソースコードを書き換えずに扱えることを目標にする。

再取り込みでは、同一ファイル・同一版を再実行しても同じ正本へ二重追加しない。原資料の改版には新旧断片の対応、廃止候補、置換候補、分割・統合関係を保持し、既に承認した要求を勝手に削除しない。全件再採番もしない。パス・セル番号だけでは改版時にずれるため、原資料版付き断片IDと安定した仕様要素IDを分ける。

### F07：正本・生成物・一括更新【先行対応】

`canonical_ownership.json`は編集正本を明記しており、この方針は維持する。問題は、本文、要求JSON、手入力別冊、履歴JSON、生成ビューの間を、現在のツールがすべて同期・検証するわけではないこと。

承認済みの同じ仕様文やパラメータを複数正本として編集しない。自由説明・背景はMD、構造化した要求・IF・パラメータは指定した正本、MD中の対応表はその生成物という所有関係を明示する。MDを正本にする表があってもよいが、機械処理する同じ情報の正本を増やさない。

生成は「全入力検査→一時領域で全ビュー生成→相互整合・鮮度検査→一括採用」とする。P08のような途中失敗で索引だけ新しくなる状態を採用しない。生成単位の入力ハッシュ・出力一覧・生成ツール版を記録する。

### F08：内容と適用条件の受入・承認【継続して必要】

取り込み時の「原文抽出OK」、内容判断の「採用候補」、要求の「承認済み」、実装の「完了」、製品の「試験済み」は別状態にする。元資料にPASSが書いてあっても、対象機種・版・条件と証拠の確認なく、新版要求の試験結果へ転写しない。

通常APIでG側制約を解除しない、全サーバ取得は宅内ルータ経由、RS-485対象はGW G側、EL接続PCSはPCS自身が取得する、という現在の設計条件を、資料移行の副作用で変更しない。変更が必要なら独立した判断事項にする。

4ロールの名称と具体的認可は別。旧Excelの「開発者○」等から量産機全機能への許可を推定しない。機能採用、機器適合、操作認可、現在実行可否は別の軸として保持する。

## 6. 推奨する取り込み・統合の流れ

```text
旧Word／Excel原本
  → 原資料登録：ID・版・ハッシュ・対象製品・承認状態
  → 構造抽出：段落／表／セル／注記／画像と取得状況
  → 候補台帳：原文と解釈を分離、1条件ごとに識別
  → 照合：R8・旧版・他資料との重複／矛盾／適用差を提示
  → レビュー：採用／条件付き／参照／不採用／保留と根拠を記録
  → 正本へ反映：SYS・機能・IF・設定・パラメータ・データ・構成
  → 要求・USDMとの対応付け：理由・階層・原子的仕様・検証
  → 5部の該当章と一覧・OQ・統合版を生成／更新
  → 整合・新旧差分・出典再現性を検査してBaseline化
```

既存USDMがある場合は、先にそのID・階層を登録して対応付ける。USDMがない場合は、既存仕様から上位要求候補を遡って作成してよいが、元の要求意図が実証されたとしない。承認後の論理関係は「要求・理由→満たす仕様」となり、作業順序が逆であっても根拠を作り替えない。

| SourceFragment | fragment_id、source_id/版、章/段落/表/セル位置、原文、文脈、抽出品質・未取得部分 |
| Candidate | candidate_id、原文断片、解釈文、要求/仕様/設計/事実等の種別、As-Is/To-Be、適用条件、確認状態 |
| MergeDecision | 対象候補、既存ID、差分種別、候補比較、採用/保留/不採用、根拠、決定者・日付 |
| Requirement/Specification | 安定ID、記述、理由又は未確認、親子関係、条件、所属章、検証、状態 |
| TraceLink | from/toのIDと版、関係型、根拠、確認者、suspect状態 |
| ImportRun/Baseline | 入力hash・抽出器版・件数内訳・未処理対象、期待旧版hash、採用版と生成物一覧 |

リンクは1対1に限定しない。同じSYSが複数USDM仕様を支える場合、又は1つの文を複数の原子的仕様へ分割する場合を保持する。`usdm_id`既存単数フィールドは互換表示として残すか、移行規則を定義する。

### 6.2 原文の処置を全件説明できること

抽出した各候補は、採用・既存と同一・参照情報・保留・不採用等の終状態又は作業状態に割り当てる。1候補の複数仕様への分割は分割関係を記録する。未対応図形やマクロ等は抽出完了数の外で忘れず、原資料の未処理一覧に含める。

「記載がなかった」「抽出器が見落とした」「読んだが対象外にした」を区別することが、網羅性の最低条件である。

## 7. 現行の5部への追加先

章数を再び大幅に増やす必要はない。仕様作成の作業規則と文書処理ツールを、GWの製品機能として混ぜない。

| 追加事項 | 主な配置案 |

| 原資料・受領版・出典位置管理 | V-07の節／規範別冊 `Source_Register` |

## 8. 最小補強の優先順位と受入条件

### 8.1 先に整備するもの

1. 原本・断片・採用判断の台帳と、候補→レビュー→採用の状態管理。
2. 固定版監査から独立したschema・参照・非空・一意性・型・双方向整合の検査。
3. 件数の自動導出と、失敗時に正本・索引・ビューを混在させない生成手順。
4. USDMの要求・理由・仕様の構造、旧IDを保持した多対多リンクと理由未確認の扱い。

原本収集・抽出候補化と並行して進められるが、採用ゲートを整える前に正本へ大量反映しない。

### 8.2 採用前の追加回帰試験案

| ケース | 完了条件 |
|---|---|
| 正当な追加 | SYS、OQ、IF、機能、試験を追加しても検査器のコード変更が不要 |
| 不正データ | 空記述、型違い、重複ID、出典／USDMの孤立参照を生成前に拒否 |
| 再取り込み | 同一原本の再実行で重複・意図しない差分がない |
| 原資料改版 | 移動・削除・文言変更を区別し、既存採用内容を無断削除しない |
| セル移動・表結合 | 旧新版の原文位置と意味の対応を追跡できる |
| 相反候補 | 未解決の矛盾は承認済みBaselineへ入れず、双方の原文を保持 |
| 不明な理由 | 推定を仮説として保持し、承認済みの理由を捏造しない |
| 一括更新失敗 | 一部だけ更新されず、前Baselineの一式に戻れる |
| 古い生成物 | JSONとMDの不一致を採用前に検出 |
| 抽出網羅 | 非表示セル・入れ子表・注記・変更履歴・画像について取得／除外／保留を説明できる |
| 往復変換 | 採用USDM形式でID・階層・理由・条件・状態が失われない |
| 大量資料 | 想定ファイル数・断片数・要求数に対し、処理時間・メモリ・差分検査範囲を計測 |

### 8.3 次に試す範囲

本格的な全量取り込みより先に、既存の「RS-485接続仕様」「設定項目一覧」「製品機能一覧」等から、小さくても表・注記・版差を含む代表資料で実抽出パイロットを行う。その選定は提案であり、今回それらの原本を確認したわけではない。
