# STD-04 要求・仕様・変更影響分析標準

## 1. 目的・適用条件

本標準は、GitHub Copilot と人が共同で開発するときに、変更の目的・対象・影響・確認方法を少ない記録でつなぐための適用提案である。
本ファイルの配置だけでは業務承認は発生しない。`MUST` は採用後の必須事項、`SHOULD` は理由を記録して変更できる原則を示す。
既存の要求仕様、外部仕様、システム仕様、設計正本を本標準が自動的に更新・置換することはない。
共通の権限・正本の扱いは [STD-01](STD-01_GOVERNANCE.md)、案件の値と参照先は [PROJECT_PROFILE](../PROJECT_PROFILE.md) に従う。

## 2. 最小単位と記録場所

- MUST: 変更を既存チケットに関連付ける。既存の要求 ID・仕様 ID・チケット ID をそのまま使い、別体系への採番し直しをしない。
- MUST: 変更対象となる製品、ハードウェア構成、ソフトウェア版、As-Is / To-Be、対象の動作方式を特定する。
- MUST: 着手の基準を、コミット、タグ、文書版または取得日時付きの正本リンクで識別する。「最新版」だけを基準にしない。
- SHOULD: 小さな変更の要求、影響分析、確認方法をチケット本文へまとめる。詳細が増えた場合だけ [T-02](../templates/T-02_CHANGE_IMPACT.md) を作る。
- MUST: 同じ説明をチケット、設計書、進捗表へ重複転記せず、正本の記録を参照する。
- SHOULD: 親チケットの共通条件を子チケットから参照し、子には差分だけを書く。

必要なつながりは次のとおり。各矢印は文書の新設ではなく、参照が追えることを意味する。

`要求・仕様 → 変更チケット → 設計判断／実装差分 → 確認結果 → 受入判断`

## 3. 変更区分と作業の継続

| 区分 | 内容 | 着手・継続の扱い |
|---|---|---|
| R0 | 説明・表示など、コード動作が変わらない低影響の変更 | 既存の作業認可内で編集・確認を継続する |
| R1 | 承認済みの要求・設計境界内で行う通常の実装・不具合修正 | 既存の作業認可内で実装・検証を継続する |
| R2 | 外部要求、設計原則、認証、安全、重要依存、永続形式、認証認可、公開 API、期日・予算等の変更 | 調査・提案・分離環境の試作を進め、境界変更は権限を持つ人が判断する |

- MUST: 拡張子や変更行数ではなく、変更の意味と影響で区分する。
- MUST: ユーザーが操作を判断する表示、制御値の単位、安全説明、外部仕様を変える場合は、表示・文書変更という理由だけで R0 にしない。
- MUST: 着手後に R2 の影響が見つかった場合、変更した区分・根拠・必要な判断を記録する。
- MUST: R2 の境界判断待ちでも、影響を限定した解析、案の比較、試験設計、分離環境の試作は進められる。
- MUST: R0 / R1 の各編集や各テストで再承認を求めない。既存認可の範囲外となった事項だけを判断対象にする。
- MUST: 未確定の要求を実装済みの仕様として扱わない。

## 4. 変更前に答える六つの質問

| 項目 | 最低限の記録 | 省略できない理由 |
|---|---|---|
| 目的 | 誰のどの問題・要求に対応するか | 実装の必要性を判定するため |
| 現状と変更後 | 現在の挙動、期待する挙動、維持する条件 | 修正と仕様追加を区別するため |
| 対象 | 対象版・方式・モジュール・インターフェース | 作業と検証の範囲を決めるため |
| 影響 | 直接変更、波及先、調査しても不明な範囲 | 見落としと未調査を区別するため |
| 確認 | 受入条件と確認方法 | 完了を説明可能にするため |
| 判断 | 作業認可、R2 判断、未解決点の担当 | AI が権限を補完しないため |

MUST: R0 でも目的、差分、確認方法は残す。六つの質問へ短文と既存資料へのリンクで答えればよく、六つの文書を作る必要はない。

## 5. 要求・仕様の書き方

- MUST: 要求には発生条件、主体、期待結果、適用範囲を記載する。
- MUST: 受入条件は、観測可能な結果、判定方法、必要な環境を特定する。
- MUST: 数値が決まっていない場合は `TBD` とし、決定者と必要時期を記録する。AI がもっともらしい値を埋めない。
- MUST: 正常時だけでなく、その変更に関係する入力不正、通信断、タイムアウト、再起動、競合時の期待挙動を明らかにする。
- SHOULD: 要求は目的、仕様は外部から観測できる振る舞い、設計は実現方法として分ける。小規模なら同じノート内の別見出しでよい。
- SHOULD: USDM を使用している案件では既存構造を維持し、理由・要求・仕様の対応を保つ。本標準のためだけに移行しない。
- MUST: 複数の機能にまたがる要求は、一つの共通要求を複数の実装・試験へ関連付ける。似た文章を別要求として増やさない。
- MUST: 非対象範囲が判断に影響する場合は明示する。非対象として記載しただけで既存要求の適用を免除しない。

### 5.1 受入条件の記述例

以下は記述形式の例であり、製品の新しい要求値ではない。

> 対象モード M で設定変更要求を受信したとき、要求 ID X の優先度規則に従って採用または保留し、応答と最終的な有効設定を確認できる。再起動中の扱いは仕様 S を参照する。

「安定する」「高速に動く」「問題がない」だけでは受入条件にならない。
一部の制御にある 1 秒要求を扱う場合も、対象ループ、周期の起点、許容遅延・ジッタ、観測点を既存仕様から特定する。
全通信を一律に 1 秒周期とする要求へ広げない。

## 6. 影響分析の最低範囲

MUST: 変更内容に関連する行を確認し、根拠リンクまたは短い理由を付ける。関連しない行は `対象外: 理由` とし、空欄と区別する。

| 観点 | 確認する対象 |
|---|---|
| 外部振る舞い | クラウド、HEMS、ユーザー操作、接続機器への要求・応答・通知 |
| 制御 | 指令の発生源、優先度、制御権、指令の失効、停止・復帰 |
| データ | 単位、範囲、既定値、共有データ、時刻、永続形式、移行 |
| 境界 | プロセス間通信、モジュール API、公開 API、設定ファイル |
| 競合 | 設定変更と制御、複数要求、再送、処理中の停止・再起動 |
| 通信 | タイムアウト、応答順序、通信断、再接続、キュー・資源量 |
| セキュリティ | 認証・認可、秘密情報、更新、ログ、公開ポート、依存要素 |
| 構成 | Yocto 設定、依存版、対象ハードウェア、既設・新規導入版 |
| 品質・制度 | 安全、認証対象範囲、外部契約、運用・保守 |
| 検証・運営 | 既存試験、実機、委託先、日程・費用、未調査範囲 |

- MUST: 変更ファイルだけでなく、呼出元・呼出先、参照される設定・データ、影響する試験を確認する。
- MUST: 「影響なし」は確認した対象と根拠を伴う。「検索に一致しなかった」だけで、実行時登録・生成コード等の影響を否定しない。
- MUST: 未調査は `未調査`、調査したが判断不能は `不明` として残す。
- SHOULD: 関連が小さい変更は数行の表でまとめる。網羅表の全行へ同じ定型文を書かない。

## 7. SPK-GW_HEMS の確認ポイント

次は現在のプロジェクト文脈に対する確認観点であり、実装完了・試験合格・認証済みを示すものではない。
実際の対象方式と確定要求は [PROJECT_PROFILE](../PROJECT_PROFILE.md) およびそこから参照する正本を確認する。

- MUST: As-Is と To-Be のどちらを変えるか、共通ロジックへ波及するかを特定する。
- MUST: 機能レイヤーの名称から OS プロセスの配置を推定しない。既存実装の配置を確認する。
- MUST: HEMS 側の名称は `DER Power Controller` を使用し、既存の名称が残る場合は対応を示す。
- MUST: 出力制御に関係する変更では、PCS 自身がスケジュール取得する方式と、GW が取得・管理する方式への影響を分ける。
- MUST: サーバとの通信経路は宅内ルータ経由という前提を確認する。
- MUST: GW を介さず PCS 自身が取得要求・応答を行う対象は ECHONET Lite の PCS に限定し、RS-485 接続 PCS は GW が担う前提との整合を確認する。
- MUST: 方式の選択・更新・切替、停止・再起動、通信断、制御要求の競合に変更が及ぶか確認する。
- MUST: 認証・暗号化する機器と従来機器が混在する変更では、識別、通信処理、失敗時の扱いを確認する。
- MUST: JET / JC-STAR 等への影響は [STD-10](STD-10_SECURITY_AND_SUPPLIER.md) に連携する。本標準内の判断だけで外部制度の適合性を宣言しない。

## 8. 作業・変更判断の流れ

1. 依頼を受け、既存要求と対象版を確認してチケットを作る。
2. 六つの質問へ答え、リスク区分と作業認可を確認する。
3. 実装可能な範囲を `READY` とし、[STD-03](STD-03_WORK_CONTROL.md) に従って作業を始める。
4. 設計判断が必要なら [STD-05](STD-05_DESIGN.md) の最小記録を作る。
5. 実装中に前提が変わったら、差分・影響・確認方法を同じ記録で更新する。
6. [STD-07](STD-07_VERIFICATION_AND_ACCEPTANCE.md) に従って確認し、根拠を添えて受入判断へ渡す。

- MUST: 上位の要求・設計境界を変更する判断は、変更前後、影響、代替案を確認できる形で権限を持つ人へ提示する。
- MUST: 承認結果には判断者・日時・対象・判断内容・必要な条件を記録する。会話の推測で承認済みにしない。
- MUST: 判断待ちにより作業が止まる場合は、状態を保存したまま `impediment=BLOCKED` を付ける。
- SHOULD: 関連する複数の R2 判断は、同じ判断者が評価できる範囲でまとめて提示する。

## 9. 委託先情報が必要な場合

- MUST: 自社から見えない範囲を「影響なし」としない。委託先へ対象版、変更箇所、波及先、確認結果の提示を依頼する。
- MUST: 回答の根拠が不足する場合は、追加確認事項と未確定の影響をチケットへ残す。
- SHOULD: 委託先には [T-02](../templates/T-02_CHANGE_IMPACT.md) の必要欄のみを指定する。全ソフトウェアの詳細説明を毎回要求しない。
- MUST: 脆弱性修正など期限がある作業では、一次評価・暫定策・修正版・確認結果の取得状況を [STD-08](STD-08_PROGRESS_MANAGEMENT.md) へ反映する。

## 10. 完了前の確認

- MUST: 要求と実装の食い違い、未確定の数値、未調査の影響を明示する。
- MUST: 要求・仕様の正本更新が必要な場合は、その更新チケットまたは承認記録を関連付ける。
- MUST: 実装済み、検証済み、受入済み、リリース済みを別々に扱う。
- SHOULD: 次の担当者が参照すべき資料を一つのチケットからたどれる状態にする。
