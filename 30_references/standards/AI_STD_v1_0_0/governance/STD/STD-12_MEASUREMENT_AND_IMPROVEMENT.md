# STD-12 AI協働の測定・改善標準

採用・業務承認前の標準案。適用設定は [PROJECT_PROFILE](../PROJECT_PROFILE.md) に記録する。
必須はMUST、推奨はSHOULD、任意はMAYとして [STD-01](STD-01_GOVERNANCE.md) に従う。

## 1. 目的

AIと人が協働した結果を、成果の品質、開発の流れ、人の負担、判断の遅延から確認する。
実案件を進めながら、どの入力・作業・権限ならAIへ委ねられるか、どこに人の能力が必要かを改善する。
AI生成行数、プロンプト数、PR数だけで生産性や品質を判定しない。
測定のために過大な記録作業を増やさない。既存の作業票と評価記録を優先して再利用する。

## 2. 測定の共通条件

どの数値にも、対象期間、集計時点、対象集合、単位、情報源、欠測、計算方法を付ける。
実測、ツールから取得、担当者の申告、推定を区別する。
未取得はゼロではない。小標本の割合には分母を付け、比較できない条件では優劣を断定しない。
測定値は作業・工程の改善に使い、少数事例から個人の能力や貢献を順位付けしない。
不利な事例、失敗、手戻り、未受入作業を集計から黙って外さない。

## 3. 最小の週次指標

最初は以下を候補とする。取れない値は欠測のまま理由を書き、取得方法を段階的に整える。

| 指標 | 定義・読み方 |
|---|---|
| 受入済み成果 | [STD-08](STD-08_PROGRESS_MANAGEMENT.md) の受入済み重み・進捗率と件数 |
| WIP・阻害 | 状態別の進行中件数、BLOCKED件数、主な解除条件 |
| 待ち時間 | レビュー、承認、依存、環境等の理由別の滞留 |
| 手戻り | 修正要求の件数・理由、人の修正工数、再試験の実施 |
| 期限・予測差 | 承認済み期限と最新予測の差、前提と不確実性 |
| 品質の残課題 | 受入を妨げる不具合、受入後に判明した不具合、未実施評価 |

受入件数だけでは作業規模の違いを説明できない。重み・作業種別・リスク区分も参照する。
重みは凍結した計画値であり、金額、生産性の絶対値、個人評価点にはしない。

## 4. 時間の定義を固定する

$$
L_i=t_{accepted,i}-t_{ready,i},\qquad C_i=t_{accepted,i}-t_{first\_start,i}
$$

ここで $L_i$ は認可済みREADYから受入まで、$C_i$ は初回着手から受入までの経過時間とする。
両者には待ちを含む。人の投入工数ではない。稼働時間に換算する場合は使用カレンダーを明記する。
未受入作業には確定した $L_i,C_i$ を付けず、集計時点までの滞留時間として表示する。

| 時間 | 取得・集計ルール |
|---|---|
| 人の投入工数 | 実作業の記録または申告。AIの処理待ちを自動的に人の作業時間へ加算しない |
| AI実行時間 | 呼出し・セッション等で確認できる開始終了。モデル内部の思考時間を推測しない |
| 承認待ち時間 | レビュー可能な案の提出から人の判断まで。差戻しと再提出を別区間にする |
| 依存待ち時間 | 待ち開始から解除まで。原因、待ち先、解除条件を記録 |
| 手戻り工数 | 初回成果に対する修正に要した投入工数。元の作業工数と分けて識別 |

経過時間、各Actorの作業時間、複数Actorの合計工数は別指標であり、単純に足して短縮率を作らない。
待ち理由が重なる場合、主要理由を一つ選ぶか重複区間を区別する。内訳合計を出す際は二重計上しない。
作業時刻や終了時刻が取れない場合は、取得可能な粗い粒度で記録し、その精度を明記する。

## 5. 品質の見方

評価結果は `PASS / FAIL / NOT_RUN / BLOCKED / INCONCLUSIVE` に分ける。
試験合格数だけを母数にせず、必須試験数、実施数、未実施、阻害、判定不能も併記する。
手戻りの原因は、要求不足、設計不足、実装、評価不足、環境、依存先、未特定等の範囲で記録する。
原因を確認できないときは「未特定」とする。AI起因・人起因を推定だけで確定しない。

受入後不具合は、検出時点と対象版・影響範囲を記録する。
少数の不具合件数だけで、安全性や脆弱性がないことを証明したとは扱わない。
評価・受入・配布の各判断は [STD-07](STD-07_VERIFICATION_AND_ACCEPTANCE.md) と [STD-09](STD-09_CONFIGURATION_AND_RELEASE.md) に従う。

## 6. Capabilityの記録は軽く始める

[T-10](../templates/T-10_AI_CAPABILITY_LOG.md) は任意の軽量記録とし、初期は週1件の代表例を推奨する。
全プロンプトや全会話の収集を必須にしない。このログがないことだけで作業受入を妨げない。
重大な問題や例外の記録義務は [STD-11](STD-11_RISK_AND_EXCEPTIONS.md) に従い、本ログの任意性で省略しない。

Actorは `HUMAN / AI` の双方とし、人も計画・実装・観測・評価・改善を提供する。
AIも評価案を作成できるが、人の責任者による受入判断とは分ける。
Capabilityは「要求整理」「設計」「実装」「テスト設計」「観測」「計画更新」等、具体的な仕事として記す。

最低限、次の組を集める。

- どのActorが、どのCapabilityを、どの作業と認可範囲で提供したか。
- 入力の所在と状態、必要な前提、出力とその版。
- 使用環境・ツール・モデル等の確認できる情報。モデル名が取れなければ不明とする。
- 人の投入工数、AI実行時間、修正、評価結果、判断待ち時間、原価の取得可否。
- 良かった条件、失敗した条件、再利用できる指示・確認・契約、残る限界。

入力が揃わない作業と十分に揃った作業を同じ条件の実験として比べない。
AIが自分で出した能力評価だけを根拠に、権限を拡大しない。

## 7. 原価の記録

取得できる実請求、割当費用、人の工数換算、実験的推定を分ける。
定額ライセンス費を作業へ配賦する場合は、期間・対象人数・配賦方法を明記する。
トークン数や従量課金額が見えない環境では「取得不可」とし、架空の料金表で補わない。
人の時間単価が未設定なら、人時だけを記録してもよい。
金額比較では、前提の異なる実測原価と推定原価を同じ精度で表示しない。

## 8. 改善の進め方

1. 観測から課題を一つ選ぶ。事実と原因仮説を分ける。
2. 改善仮説、変更するもの、期待する効果、悪化させたくない指標を決める。
3. 既認可の小さい範囲で試し、対象作業、条件、観測期間を記録する。
4. 受入までの時間、品質、人の確認・修正負担等で評価する。
5. 継続、変更、取りやめを理由付きで決め、必要なら標準・テンプレートの改訂案を作る。

試行の規模や期間の固定値は必須にしない。初期の比較期間を置く場合も推奨設定として扱う。
改善で要求、認可境界、納期・予算の約束、採用済み標準が変わる場合は必要な人の変更承認を得る。
単なる可視化や既認可R0/R1の作業改善は、毎回承認を取り直さず継続できる。
観測を整える前に改善効果を断定しない。効果未確認の案は「仮説」「試行中」と表示する。

## 9. 比較を誤らないための条件

比較では、作業種別、規模、既存コードの理解度、入力品質、リスク区分、担当体制、評価範囲を添える。
導入前の実測がない場合、「何％向上した」と断定しない。担当者の推定なら推定と明記する。
成功した事例だけを選んだ集計を、全体の平均と呼ばない。
平均値を使う場合は件数と範囲を示す。標本が少なければ事例比較を優先する。
修正を人が肩代わりした時間、受入待ち、未完了案件を除いてAIの速さを評価しない。
早く作成できても、評価不足や受入後不具合が増えた場合は、その両方を報告する。

## 10. 最初の半年で残す資産

以下は実案件から収集するための推奨観点であり、新たなリリース約束や必須の導入日程ではない。

| 観点 | 残すもの |
|---|---|
| 入力条件 | 要求・設計・コード・試験のどの情報が揃うと委譲しやすいか |
| 出力契約 | 成果物、必要な証拠、判定方法、既知の限界 |
| Actorの役割 | 人/AIが実際に提供した能力と、協働の分担 |
| 運用条件 | 認可範囲、修正や再試行、判断待ち、依存先調整 |
| 効果と費用 | 品質、受入までの流れ、人の負担、取得できる原価 |
| 改善資産 | 再利用できる指示、テンプレート、チェック項目、失敗条件 |

SHIRABEは、将来の開発運用を支える先行製品として接続を検討できる。
HIBIKIとの接続では、人とAIが共通の参加契約を持つActorとして多様なCapabilityを提供する前提を維持する。
人を最終レビュー要員だけに限定しない。
このSTDでは、独自JSONプロトコルや未導入ランタイムを必須にしない。Markdownの安定IDと参照から始める。
将来接続の設計・導入・認可は、実装済みであると仮定せず、別の変更作業として扱う。

## 11. 保存範囲と共有

秘密情報、資格情報、個人情報をCapabilityログへ複製しない。必要な範囲の参照と要約を優先する。
アクセス権、保管先、保管期間、社外提供の可否はプロジェクト設定と組織ルールに従う。
生成AIの原文保存が認められない場合は、許されるメタデータと評価結果だけを残す。
改善用データを、承認なく別組織への説明や外部サービスへの入力に再利用しない。
