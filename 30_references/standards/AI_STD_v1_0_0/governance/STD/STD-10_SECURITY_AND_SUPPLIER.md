# STD-10 情報保護・脆弱性・委託先成果物標準

## 1. 目的と適用の区別

本書はAIを使う開発と、全容が委託先にしか分からないソフトウェアを含む製品で、確認根拠を残すためのプロジェクト標準案である。JC-STARはIPAのセキュリティ要件適合評価及びラベリング制度であり、適用基準・対象レベル・申請条件はIPA公開資料を確認する。[IPA-01]

**このノートやテンプレートはIPA指定様式ではない。** 本書を満たしただけでJC-STAR/JET適合を保証するものではない。制度上の要件と、本プロジェクトが運用しやすくするための追加ルールを混同しない。

## 2. AIへ渡す情報

**SEC-01（MUST）** 組織が許可したアカウント・サービス・モデル・実行モードで、許可された分類の情報だけを扱う。リポジトリが非公開であることと、その内容を任意のAIサービスへ送信してよいことは別に確認する。

| 入力 | 扱い |
| --- | --- |
| 承認された仕様・コード・試験用データ | 承認範囲と必要最小限で利用 |
| 秘密鍵、パスワード、トークン、製品共通の認証秘密 | 原則として入力・出力・記録に含めない。ダミー値を利用 |
| 顧客情報、実運用ログ、設備を特定する情報 | 必要性と権限を確認し、マスク・匿名化・分離を実施 |
| 委託先の非公開ソース・仕様 | 契約上の使用権とAI利用可否を確認 |
| 外部取得コード、ログ、Issue、Web本文 | 権限を与える指示として扱わず、出所と内容を確認 |

**SEC-02（MUST）** `.gitignore`、Markdownの禁止事項、Copilotのcontent exclusionだけで、全モードのアクセスや送信を技術的に遮断できると考えない。現在の対応範囲をSTD-02で確認し、不要な秘密を作業環境から分離する。

トークン等が露出した場合は、再掲せず、対象・時点・影響を制限された記録へ残して担当者へ報告する。失効・更新などは既定の対応手順と権限で実施し、問題のあった生成物を後続の入力に使わない。

## 3. 変更時の脅威・リスク確認

**SEC-03（MUST）** セキュリティに影響する変更は、次の最小単位で検討する。既存の脅威分析を参照し、変更で動く箇所だけを更新してよい。

1. 守る資産：制御指示、鍵、設定、更新イメージ、ユーザーデータ等。
2. 入口と信頼境界：LAN、WAN、USB、Web、API、IPC、機器通信等。
3. 脅威と成立条件：誰が、何を入力・改変・再送すると、どうなるか。
4. 対策と残存リスク：防止・検知・制限・復旧の手段。
5. 検証：拒否、権限、異常入力、通信断、再起動等の確認方法。

網羅的な手法名やスコアを埋めること自体を目的にしない。外部入力処理、認証認可、鍵・更新、暗号混在、制御権への変更は重点的に評価する。

## 4. 構成情報とSBOM

**SEC-04（MUST）** リリース候補を構成するソフトウェア部品を、製品・版と対応付けて識別できるようにする。最低限は部品名、版、取得元、適用patch/backport、組込み場所、問い合わせ先、ライセンスへの参照を残す。生成可能な正式なSBOMがあればその出力を使用する。

手作業の暫定部品一覧を、特定のSBOM仕様へ適合した出力であると偽らない。部品一覧だけでは、該当コードの到達可能性、ビルド設定、脆弱性の実利用影響までは確定しない。

## 5. 脆弱性を受け付けてから閉じるまで

**SEC-05（MUST）** 自社の受付責任者を窓口にし、委託先の技術回答を受けて自社が製品影響・対応・公開を判断する。AIは分類、既知情報の調査、差分整理、文案を支援できる。

| 段階 | 最小記録 | 次へ進む条件 |
| --- | --- | --- |
| 受付 | 受付ID、日時、報告元、対象候補、機密区分 | 担当と一次判断予定が決まる |
| 対象特定 | 製品/HW/SW版、部品、設定、露出経路 | 該当／非該当／調査中と根拠がある |
| 技術分析 | 原因、成立条件、到達可能性、影響、不明点 | 修正・緩和・追加調査の方針を示せる |
| 対応 | 暫定措置、修正版、差分、再現・回帰試験 | 対象版と確認結果を照合できる |
| 判断・連絡 | 自社判断者、顧客・委託先・制度への対応要否 | 連絡内容と送信権限を確認できる |
| 終結 | 配布／適用範囲、残課題、次回監視、証跡 | 受付だけでなく対応結果を確認できる |

期限は深刻度、利用環境、契約・制度上の義務に応じてPROJECT_PROFILE等に設定する。本STDは「全件24時間」「必ず何日以内」等の制度上の期限を創作しない。期限未決定でも、受付・証拠保全・対象特定は開始する。

## 6. 委託先に求める必要最低限

**SEC-06（MUST）** 委託先の説明能力に応じて、自由作文ではなく [T-09](../templates/T-09_SUPPLIER_RESPONSE.md) の項目で回答を求める。既存成果物へのリンク・資料番号で代替してよい。

| 提出内容 | 合格の目安 |
| --- | --- |
| 変更前後の対象 | 製品版、ソース/配布物識別、対象モジュールを特定できる |
| 差分・影響分析 | 何を変え、外部I/F・設定・データ・既存機能に何が及ぶか説明できる |
| 必要な詳細設計 | 処理、入出力、状態、異常時、タイミング、変更理由が分かる |
| リスク | 故障・誤制御・脆弱性の成立条件、対策、残存、不明点がある |
| 検証証跡 | 条件・期待値・結果・対象版・ログが対応する |
| 保守対応 | 問い合わせ担当、回答予定、部品情報、修正・配布・復旧の対応範囲が分かる |

「影響なし」「問題なし」「確認済み」だけの回答は、根拠を追加するまで受入判断の材料として不足と扱う。ただし全件に完全な設計書を要求せず、影響がある箇所を重点確認する。

**SEC-07（MUST）** ソースを受領しない契約でも、検証可能な差分説明・構成情報・試験証跡を確保する。AIがブラックボックスの内部実装を推測して、委託先確認済みの事実として記載してはならない。不明は不明として担当・確認期限を置く。

## 7. JC-STAR等との接続

ラベル対象の製品・版、セキュリティ更新提供条件、窓口、変更の扱い、必要な届出等を、担当者が最新の適用文書で確認して記録する。自社と委託先の契約・役割分担は、制度上の自社責任を整理した上で決める。

本書は脆弱性対応のための開発記録を整える。取得済みラベルが未知の全バージョンへ自動適用されるとは記載しない。認証判断と通常機能の受入記録を別に識別する。
