# STD-09 構成管理・依存管理・リリース標準

## 1. 再現できる単位で管理する

**CFG-01（MUST）** 要求・設計・ソース・テスト・ビルド設定・依存・実行結果を、同じ候補を指す識別子でつなぐ。Git管理ならcommit、未コミット差分があるなら追加の差分またはスナップショットIDを記録する。ソースのcommitだけで、dirtyな作業内容まで特定できると扱わない。

| 対象 | 最低限記録する識別情報 |
| --- | --- |
| 文書・計画 | ID、版、採用状態、判断記録 |
| ソース | リポジトリ、commit、ブランチ、未コミット差分の有無 |
| ビルド | ツールチェーン、設定、対象機種、生成日時、実行ログ |
| Yocto | レイヤーとrevision、MACHINE、DISTRO、recipeや設定の変更、必要なpatch |
| 配布物 | 製品版、対象HW、ファイル名、サイズ、SHA-256等の内容識別 |
| 依存 | 採用版、取得元、patch/backport、ライセンス、脆弱性判断 |
| 検証 | 候補版、試験環境、入力、実行結果、ログ |

ハッシュは内容の識別に使う。ハッシュの一致だけで、出所・署名者・承認権限を証明したことにしない。

## 2. ブランチ・PR・統合

**CFG-02（MUST）** 既存のブランチ運用をPROJECT_PROFILEに記録して使う。新規導入の初期案は、主ブランチ＋作業ブランチ＋PRである。作業ブランチ名の例は `task/TASK-001-short-name`。本標準はリポジトリ設定や保護規則を自動で変更しない。

**CFG-03（MUST）** 正式な受入対象・保護対象への統合前に、要求と差分、適用した検証、既知の未解決事項、必要な受入記録をそろえる。受入のための結合検証は、認可された検証用ブランチや隔離環境へ候補を統合して実施できる。PRの作成、PRのレビュー、検証用の統合、製品受入、正式な主ブランチへの統合、出荷を区別し、既存の統合ゲートをPROJECT_PROFILEで明確にする。

**CFG-04（SHOULD）** 利用プランと組織規程が対応する場合は、保護ブランチまたはrulesets、必要なレビュー、必要なCIチェック、不要なforce pushの制限を利用する。GitHubはこれらの制御を提供するが、利用範囲と効力は設定で決まる。[GH-07] [GH-08]

1名開発で本人が受入判断を記録する運用と、GitHubの他者レビュー要件を満たすことは同一ではない。既存の他者レビュー要件がある場合は実際のレビュー担当を確保する。レビュー不在を理由にAIが保護を解除しない。

**CFG-05（MUST）** CI画面が緑であっても、必要な試験が省略・対象外・未実行なら検証完了にしない。採用チェック名、実行元、対象commit、実際に実行された試験を確認する。必要なチェックの削除・無効化は、その変更のレビュー対象にする。

## 3. 依存追加・更新

依存追加は、必要性、代替、版固定方法、ライセンス、取得元、対象CPU/OS、更新責任、脆弱性への対応を確認する。既存依存の通常修正をすべてR2にする必要はない。暗号基盤、認証、OS主要更新、外部API・永続データへの影響等があればR2として扱う。

**CFG-06（MUST）** AIが提案したパッケージ名やAPIは、実在と対象版への適合を確認する。ビルドが通った事実だけで、配布条件や保守性を確認済みにしない。

## 4. 受入とリリースの接続

リリース時は [T-08](../templates/T-08_RELEASE_RECORD.md) により以下をそろえる。小規模な内部評価版は、適用しない項目と配布制約を明記して軽量化できる。

1. リリース対象製品・HW・FW/SW版、対象顧客または評価者。
2. 含むチケットと受入記録、承認された未解決事項。
3. ビルド識別、配布物ハッシュ、依存一覧/SBOMへの参照。
4. 必要な単体・結合・機能・実機・回帰・セキュリティ確認の結果。
5. 更新・設定移行・互換性・失敗時の復旧方法。
6. リリースノート、配布手順、リリース責任者の判断。
7. 該当時の認証・ラベル対象版への影響判断。

**CFG-07（MUST）** 配布認可がない段階でも候補と確認資料を完成させる。リリース権限を別の担当が持つ場合は、配布前にその判断を受ける。試験用実機への書込みは、対象機・復旧方法・実験範囲について有効な作業認可があれば、その範囲で実行できる。

**CFG-08（MUST）** 「ロールバック可能」は、戻す対象と操作、設定・DB・不揮発データの互換性、失敗時の復旧を含めて根拠を示す。旧FWへ戻すと危険・非互換となる場合は、承認された復旧版等の別手順を定める。

## 5. 機種・認証・実装方式の組合せ

SPK-GW_HEMSでは、対象HW、FW/SW、機器構成、ECHONET Lite/RS-485等の接続、出力制御方式、認証・暗号の有無を試験・配布構成にひも付ける。全ての組合せがサポート済みと仮定しない。

| 構成差 | リリース時に確認すること |
| --- | --- |
| PCS取得方式／GW取得方式 | 対応構成、選択条件、切替手順、重複制御の防止 |
| ECHONET Lite／RS-485 | 対象機器、制御経路、機能差、回帰対象 |
| 認証・暗号の混在 | 対応する相手、失敗時動作、設定・鍵の移行 |
| 既設機と新規機 | 適用可能版、更新経路、既知制約、対象ラベルの扱い |

JC-STARやJETへの影響判断は、担当者が適用制度・申請範囲・実際の変更を確認する。構造を分離しただけで、変更申請や説明が不要になるとは判定しない。

## 6. 証跡の保全

**CFG-09（MUST）** 受入・出荷判断に使った証跡を、設定された保管先と保持期間で保存する。訂正は元の結果と訂正理由を残す。保存期間、アクセス権、バックアップ責任が未設定なら、出荷判断までに決める。

リポジトリに大容量ログや秘密情報を無条件で置かない。アクセス制限した保管先への参照、内容識別、必要な抜粋で追跡できるようにする。
