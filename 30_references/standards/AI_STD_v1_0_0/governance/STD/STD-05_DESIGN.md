# STD-05 設計・設計判断標準

## 1. 目的・適用条件

本標準は、人と GitHub Copilot が、要求から実装へ進む際の設計判断を確認可能にするための適用提案である。
`MUST` は採用後の必須事項、`SHOULD` は理由を記録して変更できる原則を示す。配置だけでは業務承認は発生しない。
既存設計を読まずに新しい構造を正解として適用しない。正本・権限は [STD-01](STD-01_GOVERNANCE.md)、対象構成は [PROJECT_PROFILE](../PROJECT_PROFILE.md) に従う。
本標準は設計成果物の必要情報を定めるものであり、全変更に独立した詳細設計書を要求するものではない。

## 2. 設計記録の必要量

| 変更 | 最小記録 | 詳細化する条件 |
|---|---|---|
| R0 | 変更チケットの差分と確認方法 | 表示が操作判断や外部契約に影響する場合は区分を見直す |
| R1 | 変更チケット内の設計判断、関連コード・仕様への参照 | 状態、並行処理、インターフェース、異常時処理に説明が必要 |
| R2 | [T-03](../templates/T-03_DESIGN_NOTE.md) 相当の変更案、影響、比較、判断記録 | 境界変更の可否を判断できる情報と必要な専門評価を追加 |

- MUST: 既存の設計書に同じ情報があれば参照を用いる。テンプレートへ同じ内容を複写しない。
- SHOULD: 小さな変更は、図または表一つと短い判断理由で説明する。
- MUST: 文書量ではなく、実装者・確認者が同じ振る舞いを理解できるかで十分性を判断する。
- MUST: AI が提案した構造は、要求・既存コード・測定など根拠と照合するまで提案として扱う。

## 3. 設計前に確認する入力

- MUST: 要求・受入条件、対象版、対象方式、変更影響分析、関係する既存設計を確認する。
- MUST: 入力ごとに正本リンクまたは版を記録する。依頼文の要約だけを設計根拠にしない。
- MUST: 不足情報は、設計を止める事項と、仮定を明示して進められる事項に分ける。
- MUST: 既存実装から確認した事実、推定、提案、承認済み判断を文章上で区別する。
- SHOULD: 再現コードや小規模試作で確認できる不明点は、分離環境で早めに確かめる。
- MUST: 試作の成立を本番環境での成立・受入・認証の証拠に置き換えない。

## 4. 最低限、設計で答える事項

| 項目 | 必要な説明 |
|---|---|
| 責務 | 何を担うか、どこから要求を受け、どこへ作用するか |
| 配置 | どのレイヤー、モジュール、OS プロセス、実行文脈に存在するか |
| 契約 | 入出力、単位・範囲、異常値、失敗、タイムアウト、再試行 |
| 状態 | 状態の所有者、遷移条件、停止・再起動・復帰時の扱い |
| 競合 | 制御要求、設定更新、同時要求、共有データの調停方法 |
| 不変条件 | どの状況でも維持すべき条件と、その根拠 |
| 確認 | 設計判断をどの試験・観測で確認するか |

MUST: 無関係な項目は理由付きで対象外にできる。テンプレートの空欄は対象外を意味しない。

## 5. レイヤー・モジュール・プロセスを分ける

| 観点 | 記録例 | 確認したいこと |
|---|---|---|
| 論理上の責務 | Application / Usecase API / Orchestration / Control Arbiter | 何を判断するか |
| 実装単位 | ソースディレクトリ、ライブラリ、構造体、主要関数 | どのコードで実現するか |
| OS 上の配置 | Core、Energy Management 等の実在するプロセス | どの障害・権限・通信境界に属するか |
| 実行文脈 | スレッド、イベントループ、周期処理、コールバック | 何と同時に実行されるか |

- MUST: レイヤー名だけを根拠にプロセス分離・中央集約を断定しない。
- MUST: SPK-GW_HEMS の As-Is は調査した配置を記録する。Core 以外に存在する責務を消した構成図を現状図にしない。
- MUST: As-Is と To-Be の図・表には対象を明記する。移行中は併存する経路と切替条件を示す。
- SHOULD: 同じ責務が複数のプロセスにある場合は、分散する理由と整合維持方法を確認する。
- MUST: 統合・分離を変更する場合は、障害波及、データの所有、制御権、通信遅延、移行への影響を評価する。

## 6. インターフェース契約

- MUST: 変更する契約には、呼出主体、受信主体、要求内容、成功条件、失敗条件を記載する。
- MUST: 数値には単位・範囲・既定値を付け、無効値・欠損値・古い値の扱いを定義する。
- MUST: 通信や非同期処理では、応答、受理、処理完了、実機反映のどれを通知するか区別する。
- MUST: タイムアウト、再送、重複、順序逆転、遅延した応答が関係する場合は扱いを記載する。
- MUST: 再試行可能な操作では、同一要求の再実行で副作用が重複しないか確認する。
- MUST: 公開 API、永続形式、互換性、認証認可の変更は R2 の境界判断と関連付ける。
- SHOULD: 既存の型・エラー表・状態定義を参照し、同じ値を別の表へ手入力しない。

## 7. 状態・競合・データの所有

- MUST: 変更が関係する状態には、所有者、読書きする主体、有効な更新経路を示す。
- MUST: 共有データを複数の主体が更新する場合は、整合性と排他・直列化の方法を記録する。
- MUST: 競合し得る要求には、優先度、制御権、保留・拒否・中断・失効の規則を明らかにする。
- MUST: 優先順位や保護動作は承認済み要求を根拠とし、AI が「一般的には安全そう」という理由で新設しない。
- MUST: 高優先度の処理中に設定変更を受けた場合の採用時点と、重大故障等の例外条件を区別する。
- MUST: Blackboard、Mediator、RPC を利用する場合も、最新値・有効値・要求中の値の関係を曖昧にしない。
- MUST: 停止、タイムアウト、プロセス再起動、通信断の後に、古い要求や権利が残存するか確認する。
- SHOULD: 状態遷移表またはシーケンス図を用い、コード全文の言い換えを避ける。

### 7.1 状態遷移表の最小形

| 現在状態 | 入力・発生条件 | 判定・動作 | 次状態 | 観測・試験 |
|---|---|---|---|---|
| 既存状態名 | 設定変更／制御要求等 | 既存規則への参照＋今回の差分 | 既存状態名 | 応答、ログ、有効値等 |
| 停止・復帰関連 | 通信断／再起動等 | 保持・破棄・復元等の条件 | 既存状態名 | 復帰後の指令・設定等 |

## 8. 時間・資源・異常時の設計

- MUST: 周期処理を変える場合は、周期、起点、許容遅延、処理の打切り、遅延後の扱いを要求に結び付ける。
- MUST: 一部の 1 秒制御要求を、全機器・全通信へ広げない。
- MUST: 通信キューや待ち行列を変える場合は、上限、優先度、溢れた場合の扱いを示す。
- MUST: タイムアウト・再試行の設計では、全体の待ち時間と他の制御への影響を確認する。
- MUST: 異常時動作は、検出方法、影響範囲、通知、復旧条件、復旧後の状態まで示す。
- MUST: 異常時に出力を停止・保持・制限する等の判断は、製品要求と安全・出力制御上の条件に照らす。
- SHOULD: 机上では判断できない時間・資源条件は、試作での測定計画を設計に含める。

## 9. SPK-GW_HEMS の方式・移行に関する確認

以下は設計レビューの観点であり、実装構成や認証範囲を新たに確定する規則ではない。

- MUST: HEMS 側の `DER Power Controller` の責務と、出力制御に関する責務の接点を確認する。
- MUST: 出力制御方式の選択、更新、切替、無効化に関係する場合は、操作主体と許可条件を示す。
- MUST: PCS 自身がスケジュール取得する対象は ECHONET Lite の PCS、RS-485 接続 PCS では GW が担うという前提を確認する。
- MUST: PCS による取得方式と GW による取得・管理方式のそれぞれで、要求が最終的に機器へ届く経路を追えるようにする。
- MUST: 出力制御サーバとの通信経路は宅内ルータ経由として、実際の接続先・主体と照合する。
- MUST: 切替中の二重指令、未適用の設定、古いスケジュール、再起動後の方式復元への影響を調べる。
- MUST: 認証・暗号化対応の有無が混在する場合は、対象識別と通信経路の扱いを設計へ反映する。
- MUST: 既設向け変更と新規製品向け変更で適用範囲が異なる場合は、配布・移行・検証対象を分けて示す。
- MUST: HEMS と出力制御の分離方針に変更が及ぶ場合は R2 として扱い、必要な専門評価を確認する。
- MUST: 構造上の分離だけを理由に JET 等の再評価が不要と断言しない。

## 10. 設計判断とレビュー

- MUST: 選択肢が実質的に複数ある場合は、採用案、比較した案、選定理由、残るリスクを短く記録する。
- SHOULD: 比較は今回の判断を左右する二〜四項目程度に絞る。比較不要な小変更に案を捏造しない。
- MUST: R1 の既存境界内の設計調整は、既存作業認可の範囲で進める。
- MUST: R2 の境界変更は、変更内容を具体化したうえで権限を持つ人の判断に結び付ける。
- MUST: AI による設計レビューは、要求への一致、故障・競合、検証可能性など確認観点と指摘根拠を残す。
- MUST: 同じ AI の再評価や別 AI のコメントだけを、組織的に独立した審査の成立とみなさない。
- MUST: 1 名開発では、本人が別のタイミング・観点で評価したことを明記できる。実施していない別担当者レビューを記録しない。
- MUST: R2 で必要な専門性や分離が不足する場合は、責任者が専門家評価などの代替措置を判断する。

## 11. 実装への引渡しと設計更新

- MUST: 実装に必要な状態・契約・異常時動作と、検証方法が分かる状態で [STD-06](STD-06_IMPLEMENTATION.md) へ進む。
- MUST: 実装中に設計と異なる判断をした場合は、関係する設計記録または同じチケットを更新する。
- MUST: 境界が変わらない説明の補足だけを理由に作業を再承認待ちへ戻さない。
- MUST: 設計案の承認、コードの受入、ベースライン変更、リリースの判断を混同しない。
- SHOULD: 採用しなかった案は、将来の判断に有用な理由だけ残す。
