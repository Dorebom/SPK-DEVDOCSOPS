# STD-07 検証・評価・受入標準

## 1. 目的・適用条件

本標準は、変更の確認結果を証拠で説明し、実装・検証・受入を区別するための適用提案である。
`MUST` は採用後の必須事項、`SHOULD` は理由を記録して変更できる原則を示す。配置だけでは業務承認は発生しない。
人・AI は試験設計、実行、観測、評価、改善を提供できる。受入の業務上の権限は [STD-01](STD-01_GOVERNANCE.md) と [PROJECT_PROFILE](../PROJECT_PROFILE.md) で定める。

## 2. 四つの到達点を分ける

| 到達点 | 意味 | その段階だけでは言えないこと |
|---|---|---|
| 実装済み | 意図したコード・設定・文書の変更がある | 正しく動作した、受入された |
| 検証済み | 指定した対象・環境・条件で確認した | 未確認の構成でも成立する、受入された |
| 受入済み | 権限を持つ人が対象と条件を明示して受入した | 配布・本番反映・認証更新が完了した |
| リリース済み | 認可された配布・適用が行われた | 全設置先への反映や運用確認も完了した |

- MUST: 「完了」「確認済み」の記載には、対象と到達点を併記する。
- MUST: AI の回答、成功したビルド、テストの成功を受入承認に変換しない。
- MUST: ホスト試験、シミュレータ、対象実機、実運用の証拠を区別する。

## 3. 結果語彙

| 結果 | 用いる条件 |
|---|---|
| `PASS` | 定めた条件で実行し、明示した期待結果を満たした |
| `FAIL` | 実行し、期待結果を満たさないことを確認した |
| `NOT_RUN` | 実行していない。理由と今後の扱いを記載する |
| `BLOCKED` | 実行に必要な前提が満たせず、実行または完了できない |
| `INCONCLUSIVE` | 実行したが、観測不足・不安定な結果等で判定できない |

- MUST: 試験結果とチケット状態を別項目で記録する。試験の `BLOCKED` はチケット状態名ではない。
- MUST: チケット側の妨げは、元の状態を保存したまま `impediment=BLOCKED` で示す。
- MUST: 適用しない試験は、結果欄を `PASS` にせず、適用範囲の記録に `対象外: 理由` と記載する。
- MUST: 一部成功を全体成功へ読み替えない。失敗・未実施・判断不能の内訳を示す。

## 4. 確認計画の最低項目

MUST: 実装・試験前に、受入条件ごとの確認方法と必要環境を決める。小変更ではチケットの数行でよい。

| 項目 | 最低限必要な情報 |
|---|---|
| 対象 | チケット、要求・受入条件、対象版・構成・方式 |
| 方法 | レビュー、ビルド、試験、実機観測等の方法 |
| 期待結果 | 合否を判断する具体的な結果・値・状態 |
| 環境 | ホスト、対象ビルド、模擬機器、対象実機等 |
| 証拠 | ログ、試験出力、画面、測定値等の保存先 |
| 残る範囲 | 確認できない事項、補完策、必要な判断 |

- SHOULD: 既存の試験仕様を参照し、今回の差分と追加ケースだけ記録する。
- MUST: 不具合修正では、可能な範囲で不具合が存在した条件と修正後の結果を対応付ける。
- MUST: 実機でしか確認できない挙動を、ホストの単体試験だけで充足したとしない。
- SHOULD: 作業途中の適切な段階で確認し、最後に大量の未確認を残さない。

## 5. リスクと確認量

| 区分 | 確認の原則 | 記録の最小例 |
|---|---|---|
| R0 | 差分を読み、リンク・表示・説明の正しさを確認 | 差分参照＋実施した確認と結果 |
| R1 | 変更挙動と影響先を確認。必要なビルド・境界値・異常系・回帰を選ぶ | 既存試験結果＋今回の差分ケース |
| R2 | 変更する境界に必要な専門評価、構成・互換性・移行等を含める | 確認計画＋評価根拠＋権限者の判断記録 |

- MUST: 区分だけを理由に全試験を一律で要求しない。変更影響、既存の必須ゲート、確認できていない具体的なリスクで決める。
- SHOULD: 低影響の可逆な説明修正に、実装をそのまま再現する自動テストを追加しない。
- MUST: 省略する確認は、その変更で不要である理由または既存証拠を示す。
- MUST: 必要な確認ができない場合は、未確認の影響と対応を明示し、[STD-11](STD-11_RISK_AND_EXCEPTIONS.md) の判断へつなぐ。

## 6. 変更に応じた確認観点

| 観点 | 関連する変更で確認すること |
|---|---|
| 正常・境界 | 正常入力、上限・下限、欠損、不正入力、対応外機器 |
| 異常・復旧 | エラー、タイムアウト、通信断、再接続、停止・再起動 |
| 競合 | 複数要求、設定更新中の制御、高優先度処理、重複・順序逆転 |
| 状態・保存 | 初期状態、保存中断、復元、移行、古い設定・指令の残存 |
| 時間・資源 | 周期、遅延、キュー、資源枯渇、連続動作 |
| 境界・互換性 | API、プロセス間通信、対象版、既設機器、複数動作方式 |
| セキュリティ | 認証・認可、秘密情報、更新、公開面、依存変更の影響 |

### 6.1 SPK-GW_HEMS で漏れを避ける観点

- MUST: 関係する場合、As-Is / To-Be、既設版 / 新規版、対象通信・機器の組合せを明示する。
- MUST: 出力制御に関係する変更は、PCS 自身の取得方式と GW の取得・管理方式の対象を分ける。
- MUST: ECHONET Lite の PCS が GW を介さず取得する場合と、RS-485 接続 PCS に対して GW が担う場合を混同しない。
- MUST: 宅内ルータ経由の通信という前提と、試験環境の代替経路との差を記録する。
- MUST: 方式の選択・更新・切替、停止・再起動、通信断、指令競合に影響する変更では、該当する状態を確認する。
- MUST: 認証・暗号化対応機器と従来機器の混在に影響する場合、意図した対象へ正しい経路が選択されることを確認する。
- MUST: これらの試験を実施していない場合、観点を記載しただけで合格済みと扱わない。

### 6.2 1 秒制御等の時間条件を確認する場合

MUST: 対象要求から、測定点、起点、観測期間、許容条件を決める。値が未確定なら `TBD` とし、数値を捏造しない。
例えば観測点の実測時刻を $t_k$、要求周期を $T$ とする場合、周期差は次で表せる。

$$
e_k = (t_k - t_{k-1}) - T
$$

この式は測定の説明例であり、許容値や試験の合否基準を追加するものではない。
MUST: 要求の受理、通信への送出、応答、物理機器への反映のどこを測定したかを区別する。
MUST: 一部の制御で得た結果を、全通信・全機器の 1 秒動作の証拠へ拡張しない。

## 7. 実行証拠と再現性

- MUST: 確認対象のコミットまたは識別可能な差分、対象構成、実行日時、実行者を残す。
- MUST: 実行コマンド・手順・試験 ID と、期待結果・実際の結果を対応付ける。
- MUST: 生成した試験データ、模擬結果、実際の観測を区別する。
- MUST: 実行ログには不要な秘密情報・個人情報を含めず、要約で重要な失敗を隠さない。
- SHOULD: 大量ログは既存の証拠置場へ保存し、チケットには要点と参照だけを残す。
- MUST: 証拠を変更または取り直した場合、元の失敗と修正後の結果を追跡できるようにする。
- MUST: 別コミットの証拠を流用する場合は、適用できる根拠と確認対象の差分を示す。
- MUST: 自動実行の終了コードや件数だけで判定せず、必要な試験が実際に実行されたことを確認する。

## 8. 失敗・未実施・既存不具合の扱い

- MUST: `FAIL` は不一致の内容、影響、対応チケットを記録する。
- MUST: `NOT_RUN` は未実施理由、実施予定または不要とする判断先を記録する。
- MUST: `BLOCKED` は不足する前提、解消担当、次の確認時点を記録する。
- MUST: `INCONCLUSIVE` は判断できない原因と、判断可能にするための追加観測を記録する。
- MUST: 基準版にも同じ失敗がある場合は、比較結果を根拠にする。基準版の失敗という理由だけで今回の影響を否定しない。
- MUST: 修正後は影響する確認を再実行する。無関係な全体再試験は具体的な理由または必須ゲートがある場合に行う。
- MUST: 合格のために期待結果や試験対象を変える場合は、要求・確認計画を変更する正当な根拠と必要な判断を記録する。

## 9. 評価と受入

- MUST: 評価では、受入条件ごとの証拠、未確認範囲、残るリスク、未解決指摘を確認する。
- MUST: AI は評価結果と推奨を提示できるが、権限を持つ人の受入判断を代作して確定しない。
- MUST: 受入記録には対象コミット・成果物、適用構成、判断者、日時、判断内容、条件を残す。
- MUST: 権限を持つ人または委任された人の明示判断を確認してから、チケットを `ACCEPTED` にする。
- MUST: 差戻しは `CHANGES_REQUESTED` とし、再作業を `IN_PROGRESS` で行う。
- MUST: 未充足条件がある受入を検討する場合は、条件を隠さず [STD-11](STD-11_RISK_AND_EXCEPTIONS.md) の正式な例外判断を関連付ける。
- MUST: 内部の例外判断で、法令・認証・外部契約に由来する必須条件を免除したことにしない。
- MUST: 受入後でも、別途必要なベースライン変更・リリース判断を省略しない。

### 9.1 1 名開発での現実的な評価

- MUST: 実装者本人が別のタイミング・観点で評価する場合、その事実を正確に記録する。
- SHOULD: 実装中と別の観点で、要求の取りこぼし、異常系、競合、証拠の不足を確認する。
- MUST: 別の AI・別セッションによる追加確認を、人員や権限の独立性の保証と表現しない。
- MUST: R2 の判断に専門性・独立性が必要な場合は、責任者が専門家評価などの代替措置を決める。

## 10. 記録と終了条件

- SHOULD: 既存の試験記録がなければ [T-04](../templates/T-04_VERIFICATION_RECORD.md) を使う。
- MUST: 記録を完成させるために試験結果や承認者を仮置きしない。未実施・未判断を明記する。
- MUST: 必要な確認と判断が揃ったら、任意の追加検証を増やさず [STD-08](STD-08_PROGRESS_MANAGEMENT.md) の進捗を更新する。
- MUST: 受入と配布の区別を保ち、必要な次作業を [STD-09](STD-09_CONFIGURATION_AND_RELEASE.md) へつなげる。
