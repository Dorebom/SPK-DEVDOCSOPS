# 日常運用ガイド：Copilotと開発・進捗を回す

版：1.0.0／2026-10-07／STD採用時の運用案。

## 1. 最小構成は3つ

| 記録 | 役割 | 更新する時 |
| --- | --- | --- |
| 作業チケット | 何をどこまで行い、何が確認できたか | 開始・状態変化・作業終了時 |
| 証跡 | 結果を確認できるログ・成果物・レビュー | 実行・評価した時。小さければチケット内 |
| 進捗報告 | 受入済み成果、残作業、阻害、予測 | 週次と重要な状況変化 |

計画ベースラインは最初と承認された変更時に作る。全ての作業で設計書・影響分析書・リスク表を別ファイルにしない。既存資料への参照を利用する。

## 2. 最初の1件

1. [PROJECT_PROFILE](PROJECT_PROFILE.md) で対象、責任者、正本、認可範囲を記入する。
2. [T-01](templates/T-01_WORK_TICKET.md) を実際のチケット先へコピーする。既存Issue正本なら見出しを使用する。
3. 目的、受入条件、基準版、対象と非対象、R0/R1/R2、既存の作業認可を記入する。
4. Copilotへチケットと必要STDを明示して渡す。参照したファイル、対象版、不足を短く報告させる。
5. 有効な認可の範囲で、実装・検証・修正・記録まで続ける。
6. 人が結果を確認し、受入条件に照らして判断する。受入後に正式完了へ集計する。

既存の明示依頼が認可になっている場合は、その参照を残す。テンプレートを埋めるために再度同じ承認を要求しない。

## 3. 日常の時間配分の目安

以下は運用を軽くするための初期案であり、タイムシートの義務ではない。

| タイミング | 人とCopilotで確認すること |
| --- | --- |
| 作業開始：数分 | 今回のチケット、依存、基準版、受入条件、今日の成果 |
| 作業中 | 新しい事実、試験失敗、設計判断が必要な差分を記録 |
| 作業終了：数分 | 変更、実行結果、未完了、次に行う1〜3手順 |
| 週次：15〜30分の目安 | 受入済み成果、分母、残作業、阻害、次週計画、判断待ち |

AIの提案したコード行数や「進捗90%」という感想ではなく、どの受入条件が確認でき、何が未確認かを見る。

## 4. 状態の判断例

| 状況 | 正しい記録 |
| --- | --- |
| コード生成が終わった。コンパイル未実施 | IN_PROGRESS。検証はNOT_RUN |
| ホスト単体テスト合格。必須実機試験を待つ | チケットの範囲次第でIN_PROGRESSまたはIN_REVIEW。実機はBLOCKED/NOT_RUN、未受入 |
| 必須試験・レビューがそろい受入判断待ち | IN_REVIEW。受入待ちと記録 |
| 人が対象版・証跡を確認して受け入れた | ACCEPTED。判断の参照を残す |
| 実機が使えず中断した | 元stateを維持しimpediment=BLOCKED |
| コード差分はないが納期変更を提案した | 予測と変更案を記録。元の計画期限は保持 |
| リリース候補を作ったが配布していない | 候補準備済み。配布済みとは記載しない |

ホストでの実装確認だけを目的とする独立チケットなら、そこで定めた受入条件を満たして受け入れられる。その場合も製品全体の実機動作完了へ読み替えない。

## 5. Copilotへの3種類の依頼

### A. 認可済み作業を進める

```text
対象はTASK-XXXXです。PROJECT_PROFILE、該当STD、チケットと基準版を確認し、
認可済み範囲の実装・検証・修正・チケット更新まで実施してください。
設計の境界変更が必要なら、影響、代案、推奨、止まる範囲を具体化してください。
終了時に、変更、実行した確認、残作業、次の行動を示してください。
```

### B. 評価する

```text
TASK-XXXXの候補版と差分を、受入条件、設計、実際の証跡から評価してください。
観測事実と推測を分け、指摘には対象箇所、失敗条件、影響、確認方法を付けてください。
未実施・不足を明示し、受入可否は推奨として報告してください。
実装修正は、今回の評価タスクの範囲に含まれる場合だけ行ってください。
```

### C. 進捗を更新する

```text
PROJECT_PROFILEに定めた正本と採用済み計画を読み、作成時点を示して進捗を更新してください。
受入記録がある成果だけを完了に数え、固定した重みと分母で集計してください。
実装途中、試験待ち、阻害、判断待ち、残作業、完了予測を分けてください。
合意済み期日・範囲・重みは変更せず、必要な変更案を別に示してください。
外部台帳に実際にはアクセス・更新できなかった場合は、その事実を明記してください。
```

## 6. どこで判断を受けるか

通常の調査・編集・テスト・再修正は既存認可内で進める。次が必要になったら、選択肢を具体化して該当責任者へ提示する。

- 要求や外部約束、制御権、公開I/F、永続データ、安全・認証に関係する境界の変更。
- 合意済み計画、優先順位、期日、工数配分、分母の変更。
- 受入、配布、対外連絡等、実施権限が別に定まる行為。

判断待ちの間は、無関係な認可済み作業を進められる。待ち時間は「実装が遅い」と混ぜず、別に可視化する。

## 7. ドキュメントを増やす判断

| 作業 | 推奨する最小記録 |
| --- | --- |
| R0の文言修正 | T-01の目的、差分、目視確認、受入 |
| R1の小さな不具合修正 | T-01の影響・修正・再現試験・回帰・受入 |
| 状態やI/Fが複雑な変更 | T-01＋必要なT-02/T-03/T-04 |
| R2の設計原理変更 | T-02/T-03＋判断記録＋必要な検証 |
| 委託先への問い合わせ | T-09。既存資料参照で重複を減らす |

「影響なし」の根拠や必要試験を省くための簡略化はしない。書式の量を小さくすることと、確認内容を失うことを分ける。

## 8. 導入後の確認

最初の1〜2件で、チケットID、参照版、状態、検証の未実施、受入判断、週報の計算が追えるかを確認する。読み込み確認は、単にAIが「読みました」と答えたことだけで判断せず、回答と実際の差分・記録を照合する。

モデル・クライアント・拡張・組織設定を変えた時は、入口と任意プロンプトが期待通りに使えるか確認する。ファイル配置は強制制御ではないため、必要なブランチ保護やレビューはSTD-09に従って設定する。
